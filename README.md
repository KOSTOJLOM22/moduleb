### Тренировка в симуляторе вместо поля

Симулятор — сетка 6×6 с построчной нумерацией и двумя другими именами
топиков: объединённый скан `/RMC2/scan` вместо `/RMC2/scan_front` и
`/RMC2/aruco_id` вместо `/RMC2/camera_bottom/aruco_id`. Правки кода это не
требует, всё задаётся параметрами:

```bash
python3 main.py --ros-args \
  -p grid_rows:=6 -p grid_cols:=6 -p grid_order:=row_major \
  -p aruco_topic:=/RMC2/aruco_id \
  -p scan_topic:=/RMC2/scan \
  -p start_id:=0 -p target_id:=33
```

Важно: `grid_rows`/`grid_cols` и `grid_order` меняются **вместе**. Поменять
только размер — робот поедет не в ту клетку, и никакой ошибки при этом не
будет: номера останутся допустимыми, просто будут значить другое место.

`scan_topic` на поле — именно `/RMC2/scan_front`. Топик `/RMC2/scan` там
объединяет передний и задний лидары, в нём видно корпус и заднюю полусферу,
и передний сектор по нему считается неверно; в симуляторе `/RMC2/scan` —
единственный источник и подходит.

Тесты логики (запускаются где угодно, ROS не нужен):

```bash
python3 -m unittest test_navigation_core test_mission_flow
```

## Порядок зачётной попытки

Задание финала жёстко задаёт последовательность, и код ей следует. **Всё
укладывается в один скрипт** — лимит модуля Б два, второй остаётся в запасе.

| Шаг | Кто | Что происходит |
|---|---|---|
| 1 | конкурсант | `python3 main.py --ros-args -p start_id:=… -p target_id:=…` |
| 2 | робот | ждёт стартовый маркер под нижней камерой, привязывает систему координат |
| 3 | робот | печатает `МАРШРУТ к цели: [0, 5, 10, 11, 12]` в терминал **и** в лог-файл, рядом — число ячеек и поворотов |
| 4 | эксперт | фиксирует маршрут. Робот стоит, таймер не идёт |
| 5 | конкурсант | подаёт команду на движение |
| 6 | робот | `movement_start`, едет по маршруту, `movement_stop` с временем этапа |
| 7 | эксперт | выставляет на поле динамическое препятствие |
| 8 | робот | видит его лидаром, печатает `МАРШРУТ на старт: [...]` уже в обход занятых ячеек |
| 9 | эксперт | фиксирует второй маршрут |
| 10 | конкурсант | подаёт команду на движение |
| 11 | робот | `movement_start`, возвращается, `movement_stop`, печатает зачётное время |

Команда на движение — **Enter** в терминале, где запущен `main.py`.
Запасной вариант, если терминал занят:

```bash
ros2 topic pub --once /chvt/go std_msgs/Bool "{data: true}"
```

Отдельный скрипт для этого не нужен, лимит модуля в два скрипта не тратится.

Если удобнее прежнее поведение — ехать сразу после построения маршрута, без
ожидания команды: `-p wait_for_go:=false`.

## Кратчайший маршрут: определение из задания

> «Кратчайший маршрут — минимальное расстояние между стартовой и целевой
> точкой, которое считается дискретно по ячейкам соревновательного поля с
> учётом количества поворотов РМК (маршруты с равным количеством дискретных
> перемещений по ячейкам, но с разным количеством поворотов, не считаются
> равными). Поворот считается дискретно по 90 градусов.»

Отсюда `route_with_turns()`: Дейкстра по состояниям (маркер, направление
въезда), стоимость `ячейки * 1000 + повороты`. Тысяча заведомо больше любого
числа поворотов на поле 6×6, поэтому лишняя ячейка никогда не окупается.
Разворот на 180° — два поворота. Стартовый курс тоже учитывается: доворот
перед первым шагом робот делает физически.

В логе печатается число ячеек и поворотов — видно, по какому определению
построен маршрут.

## Как устроено обнаружение препятствий

Заранее вписанных «занятых» маркеров больше нет. Работает так:

1. **Привязка системы координат и борьба со сносом.** Робот стоит на стартовом
   маркере; когда нижняя камера подтверждает его ID, поза одометрии
   запоминается как якорь, а поворот поля берётся как
   `odom_yaw + π + map_angle_offset` (робот спавнится с `angle_z=3.14`).

   Дальше привязка **не остаётся статичной**. На каждом подтверждённом маркере:
   - **сдвиг обнуляется** (`reanchor`) — робот подтверждённо над маркером,
     значит замеренная камерой точка маркера и есть его координата в одометрии;
   - **угол уточняется** (`refine_theta`) — вектор пройденного отрезка в
     одометрии сравнивается с вектором между теми же маркерами в поле, разница
     подмешивается с коэффициентом `theta_gain`.

   Без этого одометрия за 8–10 маркеров накапливала несколько градусов, робот
   приходил на маркеры со смещением от центра и на возврате задевал ножку
   стеллажа.

2. **Разбор скана и поправка на фрейм.** `/RMC2/scan` — объединённый скан двух
   лидаров от `ar_dual_lidar_merge_ros2`, сектор −π…+π. Публикуется он во фрейме
   `RMC2/laser_merged`, который **повёрнут относительно `RMC2/base_link`**:
   передний лидар стоит под +30°, задний под 210°, merged-фрейм строится как
   slerp-середина между ними и получает поворот около −60°. Узел берёт этот
   поворот из TF `RMC2/base_link → RMC2/laser_merged` и приводит все точки к
   base_link. Затем отбрасываются лучи ближе `robot_radius` (корпус) и дальше
   `scan_max_range`, и считается минимальная дистанция в переднем секторе
   `front_sector_deg`.

   Без этой поправки скан развёрнут: стена, стоящая слева от робота, выглядит
   как препятствие прямо по курсу, и робот встаёт на пустом поле.

3. **Точки → маркеры.** Каждая точка скана переводится base_link → odom → поле,
   ищется ближайший маркер сетки. Если точка ближе `obstacle_radius` к центру
   маркера — маркеру засчитывается попадание.

4. **Гистерезис.** Маркер объявляется занятым, только если в нём набралось
   ≥ `min_points_per_marker` точек в `hits_to_block` сканах подряд. Один шумовой
   луч ничего не блокирует. Через `block_forget_time` секунд без подтверждений
   маркер снова свободен — препятствие убрали, поле открылось.

5. **Дальность привязки.** Точки дальше `attribution_range` (1.6 м) занятыми
   маркеры не делают. Без этого робот, стоя на маркере 1, засекал препятствие
   на маркере 3 и разворачивался, ещё не доехав до маркера 2. На дистанцию по
   курсу и на экстренный стоп ограничение не влияет — там работает весь скан.

6. **Перестроение только на маркере.** Если занят БЛИЖАЙШИЙ маркер, до которого
   едем, — останавливаемся и перестраиваем сразу. Если занято что-то дальше по
   маршруту — запоминаем, доезжаем до текущего маркера и перестраиваем уже там.
   Разворотов посреди отрезка больше нет.

7. **Экстренный стоп.** Если по курсу ближе `stop_distance` — немедленный стоп с
   записью в лог. Робот стоит, пока курс не освободится или пока лидар не
   привяжет препятствие к маркеру — выдуманных блокировок «помечаю занятым
   ближайший по курсу» больше нет, они отравляли карту. Между `stop_distance`
   и `slow_distance` скорость плавно падает.

Маркеры, которые нельзя объявлять занятыми: стартовый, последний пройденный и
тот, который виден камерой прямо сейчас (иначе робот заблокировал бы сам себя).

## Как робот держит курс

- **Курс отрезка кратен 90°.** Маршрут всегда идёт вдоль сетки, поэтому робот
  доворачивается в одно из четырёх направлений поля и держит именно его, а не
  «направление на точку». Отклонение от линии отрезка гасится отдельным
  членом регулятора (`cross_track_gain`), так что робот едет по прямой, а не
  виляет вслед за счислением. В статусной строке видно `снос` — боковое
  отклонение от линии в метрах.
- **Перепривязка при неожиданном маркере.** Если камера показала маркер,
  которого не ждали, робот считает счисление ошибочным: привязывается к тому,
  что реально видит, и строит маршрут заново от него.
- **Потеря позиции.** Если отрезок пройден более чем на `leg_overshoot` (1.6)
  длины, а маркера так и нет, робот останавливается и пишет в лог, что потерял
  позицию, вместо того чтобы уезжать дальше вслепую.
- **Ведение по замеру, а не по счислению.** Как только нижняя камера видит
  целевой маркер, узел берёт TF `RMC2/base_link → aruco_<id>` — это прямое
  измерение смещения робота от центра маркера (камера стоит на оси робота).
  Робот доводится по этому замеру до `center_tolerance`, а если маркер уже
  проехал под центром — сдаёт назад, а не крутится вокруг него.
  Заодно это закрывает аспекты «получение позиции» и «получение ориентации
  РМК-2 относительно обнаруженного aruco-маркера».
- **Допуск доворота 0.02 рад (1.1°)** вместо прежних 0.08 рад (4.6°). Старый
  допуск давал трогание с перекосом до 4.6°, а это ~8 см увода на метре пути.
- **Пауза `yaw_settle_time` после доворота**, чтобы платформа перестала
  раскачиваться до начала хода.
- **Поиск маркера.** Нижняя камера висит низко и видит пятно шириной около
  20 см, так что при небольшом сносе маркер просто проходит мимо кадра. Раньше
  робот в этом случае стоял 5 секунд и засчитывал маркер по счислению — снос
  никогда не исправлялся. Теперь он обшаривает окрестность: подаётся
  назад-вперёд вдоль отрезка и подкручивается в обе стороны, пока маркер не
  попадёт в кадр. Только если и поиск не помог, маркер засчитывается по
  счислению с явной записью в лог.
- **Финальная доводка.** На конечном маркере каждого этапа робот сначала
  подтягивается на центр до `final_tolerance` (1.5 см), потом доворачивается в
  ту ориентацию, в которой начинал миссию. Порядок важен: разворот на месте
  идёт вокруг оси робота, а камера стоит на этой же оси, поэтому доворот уже не
  сбивает наведение. Курс запоминается **в системе поля**, а не в одометрии:
  `theta` уточняется по ходу маршрута, и возврат в запомненный угол одометрии
  поставил бы робота криво ровно на величину накопленной поправки.
  Итоговые невязки пишутся в лог отдельными строками.
- **Занятость ячеек берётся только из двух источников, предусмотренных
  заданием:** графа маркеров, который выдают организаторы, и собственного
  лидара РМК-2. Номеров, привязанных к конкретному полю, в коде нет —
  `blocked_markers` по умолчанию пуст. Если эксперты объявят занятые ячейки,
  они задаются флагом при запуске:

  ```bash
  python3 main.py --ros-args -p blocked_markers:="7,8,20"
  ```

  Ограничение лидара, о котором стоит помнить: тонкую вертикальную стойку он
  ловит несколькими лучами и может не набрать `hits_to_block` подтверждений
  подряд. Если при отладке робот цепляет такую ножку, посмотрите занятые
  ячейки через `python3 scan_check.py` и объявите их явно на время теста.

## Как проверять реакцию на препятствие

### Способ 1 — диагностика без движения (основной)

Терминал 1: симулятор. Терминал 2:

```bash
cd ~/"Project Robotiki"/module_B_navigation && python3 scan_check.py
```

Раз в секунду печатается карта:

```
робот: поле x=-1.00 y=+0.00 | ближайший маркер 6 (0.03 м) | ArUco: 6
впереди: 0.62 м | точек лидара в работе: 118
занятые маркеры: [12, 13]
точек по маркерам: 12:31, 13:9
      c0 c1 c2 c3 c4 c5
r0     S  .  .  .  .  .
r1     R  .  .  .  .  .
r2     X  X  .  .  .  .
r3     .  .  .  T  .  .
...
МАРШРУТ 6 -> 33: 6 -> 7 -> 13 -> ...
```

Теперь в третьем терминале двигай препятствие и смотри, как меняется картинка:

```bash
ros2 launch ar_webots_fms_ros2 spawn_object.launch.py x:=-2.0 y:=0.0 angle_z:=0.0 object_name:=obs1
ros2 launch ar_webots_fms_ros2 spawn_object.launch.py x:=-2.0 y:=2.0 angle_z:=0.0 object_name:=obs2
```

Проверяешь: маркер под препятствием загорелся `X`, число точек по нему растёт,
маршрут в последней строке обошёл его стороной. Имя `object_name` каждый раз
уникальное — спавн с существующим именем роняет симулятор.

Можно и без спавна: прокатить робота телеоперацией к любому объекту поля и
убедиться, что «впереди» падает, а соответствующий маркер занимается.

### Способ 2 — боевой прогон

1. Запусти `python3 main.py`, дождись `ЭТАП 1`.
2. Пока робот едет к цели, поставь препятствие на его маршрут.
3. В логе должно появиться: `ЭКСТРЕННЫЙ СТОП` → `ПРЕПЯТСТВИЕ: маркер N занят` →
   `Маршрут перекрыт маркерами [...]` → `МАРШРУТ ... (перестроенный)`.
4. Убери препятствие (или переставь) — через `block_forget_time` маркер
   освободится, о чём будет запись `Маркер N снова свободен`.

### Спавн препятствия перед запуском миссии

Симулятор (терминал 1) уже работает. В отдельном терминале с теми же `source`:

```bash
ros2 launch ar_webots_fms_ros2 spawn_object.launch.py \
    x:=-2.0 y:=3.0 angle_z:=0.0 object_name:=obs1
```

`x` и `y` — координаты мира, они же координаты сетки: маркер с `id` лежит в
точке `x = -(id // 6)`, `y = id % 6`. То есть команда выше ставит препятствие
ровно на маркер 15. Команда отрабатывает за секунду и завершается — Ctrl+C не
нужен, терминал освобождается, и в нём же можно спавнить следующее.

Ставь сколько нужно, но `object_name` каждый раз новый, иначе симулятор упадёт:

```bash
ros2 launch ar_webots_fms_ros2 spawn_object.launch.py x:=-2.0 y:=3.0 angle_z:=0.0 object_name:=obs1
ros2 launch ar_webots_fms_ros2 spawn_object.launch.py x:=-3.0 y:=3.0 angle_z:=0.0 object_name:=obs2
```

После этого запускай терминал 3 с миссией — робот увидит препятствия лидаром и
построит маршрут в обход. Убрать препятствие можно только руками в дереве сцены
Webots (выделить узел и Delete) либо перезапуском мира.

### Способ 3 — самотест одной командой

```bash
python3 main.py --ros-args -p auto_spawn_obstacle:=true -p spawn_x:=-3.0 -p spawn_y:=3.0
```

Робот доедет до цели, сам поставит препятствие и поедет обратно в обход. Удобно
для отладки, но **на контрольной попытке так запускать нельзя** — препятствие
выставляет эксперт.

### Про время симулятора

Всё в симуляторе штампуется временем симулятора, а узел живёт по стенным
часам. Из-за этой разницы проверка «свежий ли TF маркера» всегда давала
«протух», и доводка по замеру камеры не включалась ни разу, хотя сам TF
находился. Теперь возраст TF считается относительно времени из заголовка
одометрии, то есть в той же шкале. В строке `ДИАГНОСТИКА` появится
предупреждение, если TF снова начнёт массово отбраковываться по возрасту.

### Если робот едет вслепую (маркеры не подтверждаются)

Через 20 секунд после старта узел пишет строку `ДИАГНОСТИКА`. Если там
`пришло всего N сообщений /RMC2/aruco_id` — детектор молчит, и вся навигация
идёт на голом счислении: снос не корректируется, маркеры засчитываются по
таймауту (`ArUco не подтвердил`). Так было в прогоне 15:31 — 0 подтверждений
камерой из 8 маркеров, отсюда и кривая езда.

Проверять так:

```bash
ros2 topic hz /RMC2/aruco_id
ros2 run tf2_ros tf2_echo RMC2/base_link aruco_0
```

Камеры Webots публикуют кадр только когда на топик кто-то подписан, поэтому
**держи запущенным rviz2 из терминала 2** — он и создаёт подписчика. Если
`aruco_id` идёт, а `tf2_echo` пусто, значит детектор публикует TF в
пространство имён `/RMC2/tf`, и доводка работает по ID (грубее, но работает).

### Если робот тормозит на пустом поле

Первым делом смотри строку `TF RMC2/base_link -> RMC2/laser_merged` в начале
лога: там печатается поворот фрейма скана. Если её нет, а есть
`Жду TF ... пока препятствия не анализируются` — TF не поднялся, лидар не
анализируется вообще. Проверь `ros2 run tf2_ros tf2_echo RMC2/base_link
RMC2/laser_merged`. Как временное решение поворот можно задать руками:

```bash
python3 main.py --ros-args -p scan_yaw_offset_deg:=-60.0
```

### Если ложно занимаются крайние маркеры

Стены поля могут попадать в радиус внешнего кольца маркеров. Признак: в
`scan_check.py` весь внешний ряд в `X`. Лечится по порядку:

1. уменьшить `obstacle_radius` до 0.25–0.30;
2. уменьшить `scan_max_range` до 2.0–2.5;
3. крайняя мера — `-p protect_border:=true`, тогда внешнее кольцо не занимается
   никогда (но и настоящее препятствие на нём не увидится).

## Карта поля (из `factory.wbt` и `ArucoMap.proto`)

Проверено по исходникам симулятора, а не на глаз:

- сетка **6×6, шаг 1 м**, `id = row*6 + col`, координаты мира `x = −row`, `y = +col`
  (карта в мире повёрнута на +90°, поэтому локальные `(col, row)` становятся
  мировыми `(−row, col)`);
- маркер 0 в точке (0, 0), маркер 35 в точке (−5, +5);
- РМК-2 спавнится на маркере 0 с `angle_z = 3.14`;
- три стенки высотой 0.4 м стоят на расстоянии 1 м от внешних маркеров:
  `x = +1`, `x = −6`, `y = −1`. В радиус `obstacle_radius` они не попадают,
  так что внешнее кольцо ложно не занимается;
- в мире симулятора часть ячеек занята мебелью (стеллажи и стол). Планировщик
  объявит их занятыми по лидару и обойдёт — это не ложное срабатывание.
  Конкретные номера зависят от версии мира и в коде не зашиты: если нужно,
  посмотрите их через `python3 scan_check.py`.

## Что ещё стоит доделать

- Сейчас препятствие занимает маркер целиком. Если оно узкое и стоит между
  маркерами, робот проедет впритирку — помогает поднять `obstacle_radius`, но
  тогда растёт риск ложных срабатываний. Правильнее считать занятым ребро графа,
  а не вершину.
- Планировщик 4-связный. Диагонали дали бы более короткий путь, но по заданию
  робот должен ехать вдоль маркеров, так что это осознанный выбор.
- `map_angle_offset` подобран под симулятор. На реальном поле его надо
  перемерить: проехать по прямой 4–5 маркеров и сверить накопленный снос.
